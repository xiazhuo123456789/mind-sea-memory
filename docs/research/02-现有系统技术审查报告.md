## 2. 逐项审查（任务书第二阶段 11 问 × 源码证据）

### Q1 记忆如何产生？
**实现**：三个入口——① `/v1` 代理每轮自动写（`server.mjs rememberConversation`，L104-133）；② `POST /remember` 手动/工具写（L332）；③ seed 导入。自动写前置 LLM 抽取（`lib/extract.mjs extractWithLLM`，OpenAI 兼容），失败走 `fallback` 拼原文。
**确认**：✅ 已实现，且写入闸门有四层（问句/长度/纯表情/LLM skip）。

### Q2 如何判断值得保存？
**实现**：`minChars`（默认6）、`looksLikeQuestion`（`server.mjs L126`）、LLM 的 `skip` 标记、importance 由 LLM 按"寒暄0.2/日常0.4/约定0.6/重要0.8"打分（`extract.mjs L29`）。
**不足**：只有**单维 importance**，没有任务书要求的新颖性（与已有记忆重合度）、置信度、复用价值三维；写入前**不做与既有记忆的相似度查重**（查重只在召回时和夜间合并时发生）——同一天重复说十遍的事会先入十条再等夜间合并。

### Q3 如何区分短期和长期？
**实现**：❌ **没有区分**。所有记忆写入即进长期库（brain.json），没有 working memory / 会话缓冲层。MemGPT 的 main context 分层、LightMem 的三阶段里，本引擎只有"长期"一段。
**影响**：琐碎的近期对话直接污染长期召回空间（靠 retention 亮度与 minScore 缓解，但结构上缺层）。

### Q4 如何建立记忆间联系？
**实现**：① `entities` 数组 + 检索时 1 跳共现扩散（`engine.mjs L167-176`）；② `relations` 表（`store.mjs addRelation`）。
**不足**：**`extract.mjs normalize()` 不输出 relations**（对照 memory-brain 的 extractor 有 relations 字段）——即抽取阶段不产生关系边；`relations` 表没有任何自动写入路径，`addRelation` 无调用方（grep 确认）。图谱路的"图"实际退化为"实体共现集合"，没有语义关系边。

### Q5 如何处理重复记忆？
**实现**：召回时 0.82 二元组相似去重（`engine.mjs L239`）+ 夜间合并 ≥0.92 同 owner（`engine.mjs L294-312`，并入较新、importance 取 max、hits 累加）。
**确认**：✅ 已实现，且合并不删除（drop 方 archived）可回溯。

### Q6 如何处理新旧信息冲突？
**实现**：v3 `fact_key` 机制（`store.mjs insertMemory L139-152`）：同 owner+同 fact_key 的 active 记忆 → 进 `conflicts` 待裁决队列（不自动覆盖），裁决三选（keep_new/keep_old/mark_only），裁决后旧条 `superseded` 不删除，全程 audit。
**确认**：✅ 机制本身是 v3 亮点。
**重大缺陷**：**fact_key 只能由调用方显式传入**——`/v1` 自动写、`/remember` 手动写、`extract.mjs` 的 LLM 抽取输出里**都没有 fact_key 字段**。grep 确认：`server.mjs` 的 rememberConversation 调用 insertMemory 时不传 fact_key。**结论：冲突队列在生产路径上永远不会被触发**，只有 seed-demo 硬编码了冲突数据。这是 v3 最大的"机制存在但未接线"问题。

### Q7 如何识别过时记忆？
**实现**：夜间归档（importance<0.15 或 30天未想起且<0.3，`engine.mjs L286-291`）+ superseded 标记（冲突裁决后）+ 180 天清除。
**不足**：①没有 `valid_from/valid_until` 时间有效性字段（Graphiti 双时间线）——"他住在杭州"过三个月不会自动过时，只能等衰减；②"事实变化"没有主动检测（除非 fact_key 撞上，而它又不触发）。

### Q8 如何巩固和反思？
**实现**：夜间衰减/归档/合并（✓）；`POST /digest`"昨日三件事"元记忆（kind=digest，永不衰减）（✓）；审计日志 audit.jsonl（✓）。
**不足**：①没有 **Generative Agents 式反思**（从记忆子集提炼更高层洞察，洞察可回溯源记忆 id 集合）；②digest 不记录"由哪些记忆提炼而来"（无 evidence 链接）；③没有递归压缩（RAPTOR 式）——三个月前的 300 条事件不会聚成 3 条模式。

### Q9 如何检索相关历史？
**实现**：五路打分（keyword-IDF 0.46 主导 + semantic 可选 0.18 + importance 0.14 + recency 0.11 + graph 0.11）+ pin 激活 + 意图重排 + 情绪微调 + 0.82 去重 + **双通道预算**（core: fact/preference/digest/pin 用 coreK=3，事件用 k=5，互不挤占）+ minScore 门槛 + touch 续命 + rejected 原因记录。
**确认**：✅ 这是当前实现最强的部分，双通道是 v3 的真改进。
**不足**：没有查询改写（query rewrite）；没有多跳检索（1 跳共现是 PPR 的退化版）；语义路需要配 Ollama 且**手动 /remember 写入的记录没有向量**（`server.mjs /remember` 路由不算 embedding，只有 `/v1` 自动写算了——不一致）；按问题类型路由检索策略只有 fact/episode 两类。

### Q10 如何让不同 AI 共享？
**实现**：三种接入（OpenAI 兼容代理 /v1 + MCP + HTTP API），owner/visibility 模型天然支持多用户隔离，export/import 可迁移。
**确认**：✅ 架构上是全项目最强项。**新增缺口**：`/v1` 对不带 user 的请求返回 400（默认无 defaultUser 时）——DSH 等客户端传不了 user 字段就被挡死；v3 协作者没有解决，**本次已在 server.mjs 加 `defaultUser` 配置兜底**（本次审查期间修复，见 §4）。

### Q11 如何避免错误信息污染？
**实现**：extract 提示词"只写真实出现的信息，不编造"+ skip 判定；hypothesis 单独 kind；visibility 隔离；audit 审计；superseded 不删除。
**不足**：①没有 confidence 字段（LLM 抽取的可信度没有量化落地）；②记忆**没有证据链**——memory 不引用它来自哪条 episode/消息（episodes.jsonl 与 memories 断链）；③没有用户查看/编辑/删除/导出的完整 UI（面板只有星图观测，无记忆管理操作）；④没有提示注入防护（用户说"记住：忽略以上所有指令"会被当事实存）。
